Technical overview

Image Processing Service

A Cloudinary-style API that fetches an image or video by URL, then resizes, crops, converts or thumbnails it on the fly. TypeScript on Fastify, sharp and ffmpeg, with a typed SDK and a spec generated from the code.

How it works

The life of a request

Every request to /process, /video/thumbnail or /info runs the same gauntlet. The order is the design: who you are, whether you're over your limit, whether the URL is signed and whether the parameters make sense are all decided before a single byte is fetched. Even an invalid request counts against the rate limit.

Interface

API surface

EndpointWhat it does
GET /processResize, crop and convert a remote image
GET /video/thumbnailGrab a frame at time seconds, then apply the same transforms (JPEG by default)
GET /infoFormat, dimensions, size and alpha of a remote image, without transforming it
GET /docsSwagger UI; the spec itself at /docs/json and /docs/yaml
GET /Every endpoint and the parameters each one accepts, with ranges and defaults
GET /healthLiveness, running and queued jobs, and whether rate limits are being enforced

Parameters follow Cloudinary's names and short aliases: width/w, height/h, format/f (jpeg, png, webp, avif, gif, tiff, or auto to negotiate AVIF or WebP from the browser's Accept header), quality/q, crop/c, gravity/g, background/b and time/t. Validation is strict on purpose: an unknown parameter gets Did you mean "width"?, and an option that would silently do nothing, like gravity=north without crop=fill, is rejected rather than ignored.

Security

Fetching URLs from strangers

The service fetches whatever URL it's handed, which makes it an obvious way to reach internal systems (SSRF). Private, loopback, link-local, CGNAT, multicast, NAT64 and 6to4 ranges are all refused, and the important part is when that's checked.

Security

Video thumbnails without the ffmpeg trap

ffmpeg normally guesses a file's format from its contents, and some formats tell it to open other files. A review of the first version showed that a "video" which is really an HLS playlist turned the thumbnail endpoint into a way to read files from the server. It was confirmed with a real exploit, fixed, and is now a regression test.

Performance

Caching and load

Bounded memory

The result cache is limited by entry count, total bytes and age, so a few huge outputs can't push the process out of memory.

Bounded work

At most one fetch-and-transform job per CPU core, plus a queue of 100. Beyond that, a fast 503 with Retry-After replaces a slow collapse.

CDN-friendly responses

Strong ETags with 304 Not Modified (lists and weak tags handled), Cache-Control on success, no-store on errors, and Vary: Accept when the format is negotiated.

Decompression bombs

Images over 100 megapixels are refused before decoding, whatever their file size.

Access

Rate limits and API keys

Rate limiting is always on (60 requests per minute by default). What changes is who a request counts against.

Optional signed URLs (SIGNING_SECRET) add an HMAC-SHA256 over the path and sorted parameters, checked in constant time and after the rate limit, so guessing signatures is rate limited too. api_key and signature are redacted from logs, and keys are looked up by SHA-256 digest so lookup timing reveals nothing about valid keys.

Contract

Errors clients can branch on

Every error has the same shape, { "error": { "code", "message", "details"? } }, with a stable code and, for bad parameters, the field that caused it. Unexpected failures become a generic 500 logged with the request id; internals never reach the client.

Developer experience

Docs that can't drift

The OpenAPI 3.1 spec isn't written by hand. It's generated from the same zod schemas that validate requests, and served from the running configuration, so MAX_DIMENSION=2000 shows up in the docs as a maximum width of 2000. When the spec was first generated, it showed the old hand-written one had already drifted in three places.

Swagger UI at /docs lets you try every endpoint in the browser with images rendered inline, an Authorize button for API keys, and a server URL that follows whichever host is serving it.

Developer experience

TypeScript SDK

A dependency-free client that works anywhere fetch exists: browsers, Node, Deno and Bun. Its option types are checked against the server's schemas, so editors autocomplete exactly what the server accepts.

import { createClient, ImageServiceError } from 'image-processing-service/sdk';

const images = createClient({ baseUrl, apiKey, retry: { attempts: 2 } });

// URLs for <img> tags; no request is made
images.url('https://cdn.example.com/cat.jpg', { width: 500, height: 300, crop: 'fill', format: 'webp' });

// Or fetch the bytes, with dimensions read from response headers
try {
  const { data, width, height } = await images.fetch('https://cdn.example.com/cat.jpg', { width: 200 });
} catch (err) {
  if (err instanceof ImageServiceError && err.code === 'SOURCE_NOT_FOUND') showPlaceholder();
}
  • Keys go in the X-API-Key header for fetches, and in the URL only for <img> tags, which can't send headers.
  • Retries honour Retry-After on 429 and 503 and never retry validation errors; ImageServiceError carries code, details and retryAfter.
  • A separate Node-only entry point, /sdk/signer, signs URLs on the server so the secret never reaches a browser bundle.

Confidence

Tests and delivery

Real outputs, no network

A local fixture server generates real images and videos at startup and serves every failure mode: 404, 500, HTML, corrupt and empty bodies, oversize files, a server that never answers, redirect loops and disguised playlists. Tests decode the output to check format, dimensions and pixel colours.

241 tests, 97.2% of lines

240 run offline in seconds; one checks shared limits against a real Redis. Coverage thresholds fail CI if coverage drops, and knip reports no unused code.

CI on three Node versions

On Node 22, 24 and 26: Biome lint, strict typecheck, spec freshness and Redocly validation, tests with coverage against a Redis service, then a Docker build and a /health smoke test.

Ready to run

A multi-stage Node 24 image running as a non-root user with a health check, a compose file with two instances sharing Redis, and every setting an environment variable validated at startup.

Judgement calls

Decisions and trade-offs

Cloudinary defaults

crop=scale and keeping the source format by default, so people who know Cloudinary aren't surprised.

Strict over lenient

A typo like widht=500 fails loudly instead of quietly returning the full-size image, which is the kind of bug that's hard to trace. Explicit default values are always accepted, because generated clients send them.

Fail open on Redis

Availability wins over strict limits during a Redis outage, and the state is visible on /health for alerting.

Fixed windows

Simple and one round trip per request. The burst at a window boundary is absorbed by the job limiter.

Per-instance cache

Good for one instance and stated as such. At scale, a CDN sits in front and the LRU gives way to a shared store behind the same interface.

Biome, not ESLint

typescript-eslint doesn't support TypeScript 7 yet; Biome lints and formats without depending on the compiler's API.
